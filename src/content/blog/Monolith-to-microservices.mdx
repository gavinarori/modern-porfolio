The monolith wasn't badly written. It was just fifteen thousand lines of
interconnected code where changing the billing module had a 30% chance of
breaking notifications. Nobody planned that — it just accumulated, the way
these things do.

## Cutting along the right seams

The instinct is to split by technical layer — auth service, database service,
notification service. That's almost always wrong. We split by business
capability instead, and kept each service owning its own data:

```text
/services
  /billing        # owns subscriptions, invoices, payment webhooks
  /notifications  # owns email/SMS delivery, templates
  /users          # owns accounts, auth, sessions
  /catalog        # owns products, pricing
```

Each service got its own database. No shared tables, no reaching across
boundaries to "just grab one field" — that shortcut is exactly how the
monolith got tangled in the first place.

## The strangler fig, not a rewrite

We didn't stop shipping features for six months to rebuild everything. New
traffic was routed through a thin gateway that decided, per-route, whether
the monolith or a new service handled the request:

```ts
app.use("/api/billing", async (req, res, next) => {
  if (FLAGS.billingServiceEnabled) {
    return proxy(req, res, BILLING_SERVICE_URL)
  }
  next() // fall through to the monolith
})
```

That let us migrate one capability at a time, roll back instantly if
something broke, and prove each service in production before removing the
old code path.

## What broke, and what we'd do differently

- **Distributed transactions.** We underestimated how often billing and
  notifications needed to happen atomically. An event queue with retries
  solved it, but we should have designed for it from day one.
- **Local dev got harder.** Docker Compose with all services running was slow
  to start. A "stub mode" that mocked downstream services saved a lot of
  developer time.
- **Observability had to come first, not last.** Distributed tracing across
  services wasn't optional once requests started hopping between them — we
  added it too late and paid for it in debugging time.

> If I started this migration again, the very first thing I'd build is
> tracing and structured logging — before a single service gets split out.

## The outcome

Deploys went from a single 45-minute pipeline that touched everything, to
independent deploys per service averaging under 5 minutes. More importantly,
a bug in the notifications service can no longer take down checkout — which,
looking back, was really the whole point.
