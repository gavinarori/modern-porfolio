Every project starts the same way: a handful of buttons, a card, maybe a modal.
Six months later you've got four slightly different button components scattered
across three repos, and nobody remembers which one is "the real one."

This is the story of how I stopped that from happening — the structure, the
rules, and the tooling that made a component library something teams actually
reused instead of forked.

## Start with primitives, not features

The biggest mistake I made early on was building components around a specific
screen instead of a general shape. A `UserCard` is a feature. A `Card` with a
composable header, body, and footer is a primitive — and it's the difference
between a library that scales and one that becomes dead weight.

- Primitives own layout, spacing, and interaction states
- Feature components compose primitives, they don't duplicate them
- If a prop only makes sense for one screen, it doesn't belong on the primitive

## A pattern that actually held up

Compound components turned out to be the right abstraction for anything with
internal state — tabs, accordions, menus. Consumers get flexibility without
the library needing to predict every layout they'll want.

```tsx
function Tabs({ children, defaultValue }: TabsProps) {
  const [value, setValue] = useState(defaultValue)
  return (
    <TabsContext.Provider value={{ value, setValue }}>
      <div className="flex flex-col gap-2">{children}</div>
    </TabsContext.Provider>
  )
}

Tabs.List = function TabsList({ children }: { children: React.ReactNode }) {
  return <div className="flex gap-1 border-b border-white/10">{children}</div>
}

Tabs.Trigger = function TabsTrigger({ value, children }: TabsTriggerProps) {
  const ctx = useContext(TabsContext)
  const active = ctx.value === value
  return (
    <button
      onClick={() => ctx.setValue(value)}
      data-active={active}
      className="px-4 py-2 text-sm data-[active=true]:text-white text-white/50"
    >
      {children}
    </button>
  )
}
```

Consumers assemble exactly the tab bar they need, and the state management
never leaks into their code.

> The test I use now: if a component needs a prop like `variant="user-profile"`,
> it's not a primitive anymore — it's a feature wearing a primitive's clothes.

## What made adoption stick

Documentation and a changelog got us started, but three things actually moved
the needle on teams choosing the shared library over rolling their own:

| Practice | Impact |
| --- | --- |
| Visual regression tests on every PR | Caught breaking changes before release |
| A Figma library kept 1:1 with code | Designers and engineers stopped drifting apart |
| Semantic versioning + migration codemods | Upgrades became a non-event |

None of this is glamorous. It's the boring infrastructure work that makes a
component library something people trust enough to build on top of.

## Where it's headed next

I'm currently moving the library toward CSS variables for theming instead of
prop-driven variants, which should cut the API surface roughly in half while
making dark mode and white-labeling nearly free. More on that once it ships.
